# seabed

S3 같은 오브젝트 스토리지를 원본으로 두는 **오픈소스 벡터 + BM25 검색 엔진**을 만들어 보는 연구 프로젝트입니다.
turbopuffer처럼 싸고 운영이 단순하면서, 오픈소스이고 큰 namespace와 잦은 대량 갱신에서도 비용이 무너지지 않는 것을 목표로 합니다.

> **상태: 설계 단계입니다. 동작하는 검색 엔진은 아직 없습니다.**
>
> | 구분 | 상태 |
> | --- | --- |
> | 설계 문서 (요구사항, 아키텍처, 평가 계획) | 있음 → [docs/PLAN.md](docs/PLAN.md), [docs/DECISIONS.md](docs/DECISIONS.md) |
> | 코드 | M1 골격만 있음: ObjectStore 포트와 메모리 어댑터, 단일 노드 WAL, manifest 커밋, conformance 테스트 |
> | 벡터 인덱스, 필터링, BM25, 분산, API | 계획만 있고 구현하지 않음 |

## Why — 왜 만드는가

### 겪은 문제 (작성자의 운영 경험)

| 시스템 | 문제 |
| --- | --- |
| Elasticsearch HNSW | 문서가 늘면 메모리가 금방 한계에 닿고, 업데이트가 매우 비효율적이라 포기 |
| Vespa | ES보다 낫지만 메모리가 큰 노드를 비싸게 운영해야 함 |
| 주기적 대량 재색인 (ES 6노드, 200TB) | 메모리가 가득 찬 클러스터를 죽이지 않으려고 throttle해서 전체 색인에 일주일. 병렬 호출을 늘려도 노드를 늘리지 않으면 의미가 없었음 |
| ES 운영 | master 노드 한 대가 빠지면 클러스터가 불안정해짐. force merge 중 OOM으로 노드가 죽은 뒤 복귀하지 못함 |
| turbopuffer (비공개 SaaS) | 비용이 싸고 성능은 acceptable. 다만 한 namespace에 문서가 많아지면 비용이 크게 늘고, 오픈소스가 아님 |

### 이미 있는 오픈소스는 왜 안 되는가

조사한 범위(2026-10, 웹 문서 기준)에서 확인한 것과 아직 모르는 것을 나눠 적습니다. 자세한 근거는 시장 조사 문서(docs/LINKS.md)에 있습니다.

- **확인한 것:** 기본 기술은 업계가 이미 같은 방향으로 수렴했습니다. HNSW 중심에서 클러스터(IVF) 인덱스와 강한 양자화로, 쓰기 경로는 오브젝트 스토리지 WAL로 이동 중입니다. 그래서 "오브젝트 스토리지 기반 클러스터 인덱스"만으로는 차별점이 아닙니다.
- **확인한 것:** 오픈소스 분산 구성은 대체로 무겁습니다. Milvus 클러스터는 Kubernetes, etcd, 오브젝트 스토리지, WAL 계층이 필요하고, Chroma 분산은 Kubernetes/Helm과 Postgres가 필요하며, LanceDB의 대규모 분산은 Enterprise 기능이고, VectorChord는 단일 노드 Postgres입니다.
- **모르는 것:** 위 구성의 복잡함이 실제 운영 난이도 차이로 이어지는지, 그리고 대량 재색인을 서비스 노드와 분리하는 기능이 다른 시스템에 없는지는 **확인하지 못했습니다.**

### 가설 (아직 증명되지 않음)

> **simple but efficient(비용과 성능 모두)한 분산 시스템.** 기존 시스템은 기존 primitive 위에 기능을 올려서 사용자가 기존 기능을 그대로 쓸 수 있다는 장점이 있지만, 구성이 복잡하고 문제가 생기면 운영이 어렵다.

이 가설이 틀리면 이 프로젝트의 존재 이유가 약해집니다. 그래서 먼저 측정으로 확인합니다([How](#how--어떻게-만들고-검증하는가) 참고).

## What — 무엇을 만드는가

### 목표 (모두 계획이며 구현되지 않음)

- 억 단위 이상 벡터를 **낮은 비용**으로 저장하고 검색 (p99 1초 이하, 비용은 turbopuffer와 comparable)
- **필터를 1급으로**: 모든 검색에 필터가 붙고, 필터가 남기는 비율이 10%든 0.01% 이하든 recall@10 90~95%를 목표로 함
- **실시간 업데이트**: 벡터 변경과 메타데이터 변경을 구분해서 처리
- **벡터 + BM25 하이브리드**, 한국어 지원 필수
- **문서당 multi-vector** (item 하나가 여러 벡터를 가짐)와 group-by
- **대량 갱신이 서비스를 건드리지 않음**: 서비스 노드와 분리된 워커가 빌드하고, 예상 시간과 비용을 먼저 보여 줌
- S3의 원본 파일을 외부 엔진이 읽어 분석(OLAP)할 수 있음
- turbopuffer와 공통 기능은 API 호환, 구성 요소는 포트로 분리해 교체 가능
- Rust, 모니터링은 OpenTelemetry

### 쓰지 않는 편이 좋은 경우

| 상황 | 대신 고려할 것 | 이유 |
| --- | --- | --- |
| 벡터가 1천만 개 이하 | pgvector, VectorChord, Qdrant 단일 노드 | 더 단순하고 성숙함 |
| 테넌트(에이전트)마다 작은 namespace가 아주 많음 | Weaviate 멀티테넌시, turbopuffer 등 | 이미 그 구간에 맞춰져 있음. seabed의 목표 구간이 아님 |
| 풀텍스트 검색, 집계, 보안 기능이 핵심 | Elasticsearch, OpenSearch | 기능이 훨씬 풍부함 |
| 지금 당장 프로덕션이 필요함 | 성숙한 기존 제품 | seabed는 연구 단계 |

## How — 어떻게 만들고 검증하는가

### 구조 (계획)

```
client
  │  turbopuffer 호환 API + 확장
  ▼
쿼리 노드 (상태 없음, 로컬 캐시)          빌드 워커 (임시, 서비스와 분리)
  │  planner, 인덱스 + 미인덱싱 꼬리 병합     │  인덱스 빌드, 컴팩션, bulk 적재
  └──────────────────┬────────────────────┘
                     ▼
            오브젝트 스토리지 (S3)
            WAL · manifest(버전) · segment
            벡터 / 속성 / 텍스트 인덱스
```

별도 코디네이터 노드가 없고, 메타데이터 일관성은 S3의 조건부 쓰기(If-None-Match, If-Match)로 맞춥니다 **(제안, 검증 필요)**.

### 핵심 아이디어 (모두 계획)

1. **원본과 인덱스를 분리한다.** 원본(SoT)은 S3의 불변 segment와 manifest이고, 모든 인덱스는 원본에서 파생됩니다. 인덱스를 다시 만들어도 원본은 그대로입니다.
2. **쓰기는 WAL, 읽기는 "인덱스 + 아직 인덱싱 안 된 꼬리" 병합.** 쓰기가 성공하면 바로 검색에 보이는 strong 일관성을 기본으로 하고, 쿼리별로 eventual을 고를 수 있게 합니다. 이 방식은 turbopuffer 문서로 확인한 설계를 따릅니다.
3. **클러스터 인덱스(SPANN/SPFresh 계열) + 양자화 + 재순위.** 클러스터 단위로 읽어서 S3 왕복 횟수를 줄입니다.
4. **필터는 인덱스와 협력.** 필터가 남기는 비율에 따라 전략을 바꾸는 플래너를 둡니다(아주 적으면 정확 계산, 중간이면 클러스터 선택 후 필터, 거의 다 통과하면 일반 검색 후 필터).
5. **대량 갱신은 서비스와 분리.** 변경 비율을 측정해 증분, 부분 재빌드, 전체 재빌드 중 파티션 단위로 고르고(기본 목표는 비용 최소화), 예상 시간과 비용을 먼저 보여 준 뒤, 끝나면 manifest를 교체해 한 번에 공개합니다.

### 예: 주기적 전체 갱신

| | 기존(ES) | seabed 계획 **(가설, 측정 전)** |
| --- | --- | --- |
| 인덱싱을 하는 곳 | 서비스하는 노드 | 별도의 임시 워커 |
| 클러스터가 죽는 것을 막는 방법 | 요청을 throttle | 서비스 노드는 완성된 결과물만 읽음 |
| 걸리는 시간 | 200TB에 일주일(시간당 약 1.2TB) | 1차 목표: 10배 이상. 측정 전 |
| 공개 | 색인 중 상태가 섞임 | manifest 교체로 한 번에 |
| 실패하면 | 노드가 죽고 복귀 못 한 적 있음 | 워커 작업이 파티션 단위라 해당 작업만 재시도 **(설계 의도, 미검증)** |

**이게 실패하는 경우:** 변경 비율이 매우 높고 워커 수를 늘리기 어렵거나, S3 요청 비용(PUT)이 컴퓨트 절감을 넘어서거나, 견적이 크게 틀려서 사용자가 신뢰하지 못하는 경우.

### 검증 방법: M0

설계가 맞는지는 만들기 전에 측정으로 확인합니다.

- 기준선 시스템: Chroma, Lance, Milvus, Qdrant, VectorChord (turbopuffer는 공개 가격과 계산기로 추정)
- 시나리오: 필터 난이도 스윕, 배치 쿼리, multi-vector, 업데이트 혼합, bulk 적재 중 쿼리 간섭, 규모별 비용, BM25, **운영 단순성과 장애 복구**(노드 종료, 메모리 제한 하의 대량 병합)
- 성공 기준: recall@10 90~95%(필터 포함, 난이도 구간별 최약 기준), p99 1초 이하, 비용 turbopuffer와 comparable
- **기준선이 이미 이 기준을 만족하면** 새로 만들지 않고 기여나 재사용으로 방향을 바꿉니다.

### 개발 순서

1. 단일 노드에서 correctness를 확보한다.
2. 단일 노드 안에서 shard와 분산 구조를 구현한다.
3. 실제 분산 노드로 확장한다.

M0(평가)를 진행하면서 M1의 기본 단위를 병행합니다. 마일스톤은 [docs/PLAN.md](docs/PLAN.md)에 있습니다.

### 저장소 구조

```
crates/
  domain/                  도메인 타입과 키 레이아웃 (tenant, namespace 포함)
  ports/                   ObjectStore 트레이트와 능력 선언
  adapter-objectstore-mem/ 메모리 구현, 요청 수 계수, 장애 주입 데코레이터
  engine/                  WAL(LSN 선점), manifest 커밋
  conformance/             어떤 ObjectStore 어댑터에도 돌리는 공통 테스트
docs/
  PLAN.md                  프로젝트 계획 (요구사항, 아키텍처, 마일스톤, 열린 질문)
  DECISIONS.md             결정 기록 ([결정]/[제안]/[미정] 구분)
  LINKS.md                 설계 문서와 조사 문서 링크
```

빌드와 테스트:

```
cargo test --workspace
```

(Rust 1.70 이상, 외부 크레이트 없음. 표준 라이브러리만 사용합니다.)
