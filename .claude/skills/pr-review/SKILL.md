# PR 머지 전 리뷰

`develop`으로 가는 PR은 이 절차를 거친 뒤에만 머지한다. 문서만 바꾼 PR도 같다. 릴리스 PR(`develop` → `main`)은 이미 리뷰를 거친 PR만 담으므로 이 절차를 생략한다.

## 1. 준비

- PR 번호, head 커밋, base를 확인한다.
- 로컬을 head 커밋으로 맞춘다(`git fetch origin` 후 PR 브랜치를 체크아웃).
- CI가 아직 돌고 있으면 기다리지 말고 리뷰를 먼저 시작해도 된다. 머지 전에는 CI 통과가 필요하다.

## 2. 별도 에이전트로 리뷰

리뷰는 PR을 만든 에이전트가 스스로 하지 않는다. `pr-reviewer` 에이전트(`.claude/agents/pr-reviewer.md`)를 새 컨텍스트로 띄운다.

- 그 에이전트 타입을 쓸 수 없는 환경이면, 범용 에이전트를 띄우고 `.claude/agents/pr-reviewer.md`의 본문을 그대로 지시로 넘긴다.
- 넘길 것:
  - PR 번호, base(`origin/develop`), head 커밋
  - PR이 해결하려는 목표 한두 문장(이슈나 PLAN 항목). 작성자가 "검증했다"고 주장한 내용은 넣지 않는다.
  - 재리뷰라면 이전 보고서 전문과 이전 head sha
- 리뷰어가 돌려준 보고서는 고치지 않고 그대로 쓴다.

## 3. 결과 공유

- 보고서를 사용자에게 보여 준다. 판정, 확신 점수, 근거, 제안 표를 빼먹지 않는다.
- 보고서를 PR에 코멘트로 남긴다. 다른 사람도 머지 근거를 볼 수 있게 하기 위해서다. 코멘트 끝에 AGENTS.md의 footer를 붙인다.
- 작성자가 리뷰어의 지적에 동의하지 않으면, 보고서는 그대로 두고 반론을 "작성자 의견"으로 따로 사용자에게 보여 준다. 채택 여부는 사용자가 정한다.

## 4. 제안 반영

- 제안(5번 항목)이 있으면 사용자에게 어떤 것을 추가할지 묻는다. 여러 개를 고를 수 있게 하고, 각 선택지에 비용과 점수 변화를 함께 보여 준다.
- 1~3번 지적 중 "이 PR에서"로 분류된 것도 같은 방식으로 사용자에게 묻는다.
- 사용자가 고른 것만 같은 PR 브랜치에 추가한다.
- 고르지 않은 것은 PR 코멘트에 "보류"로 남기고, 후속 PR이나 이슈로 남길지 사용자에게 묻는다. 후속 PR 본문에는 원래 PR 번호와 보류 항목을 적는다.
- 단, "이 PR에서" 지적은 고르지 않았다는 것만으로 보류가 되지 않는다. 항목마다 보류할지 사용자에게 확인받는다(5장 세 번째 조건).
- 리뷰어가 "[결함]"으로 표시한 지적(이 PR의 커밋이 새로 만든 버그나 틀린 문서)은 기본으로 고친다. 고칠 목록을 사용자에게 먼저 보여 주고, 사용자가 명시적으로 보류를 고른 것만 뺀다. 결함인지는 작성자가 아니라 리뷰어 보고서로 정한다.
- 추가한 뒤 fmt, clippy, test를 다시 돌리고 push한다.
- CI가 실패하면 원인을 고쳐 push한다. CI를 통과시키려고 테스트를 끄거나 건너뛰지 않는다.
- 사용자가 더 추가할 것을 고르지 않으면 제안 반영 단계는 끝난다.

### 재리뷰

- push로 head가 바뀌면 리뷰어를 다시 띄운다. 테스트만 추가한 경우도 같다. 새 테스트도 "동작을 지우면 실패하는가"로 검증해야 하기 때문이다.
- 새 리뷰어에게는 이전 보고서와 `git diff <이전 head>..<새 head>`를 함께 넘긴다.
- 예외: 내용 변경 없이 base만 따라잡은 경우에는 검사만 다시 돌린다. `git fetch origin` 후 `diff <(git diff origin/develop...<이전 head>) <(git diff origin/develop...<새 head>)`의 출력이 비어 있을 때만 이 예외를 쓴다(`Cargo.lock`도 비교에 포함). 그리고 "재검사만 함, 기준 보고서 <sha>"라고 PR에 남긴다. 이 따라잡기도 5장의 조건부 사전 승인에서는 "사용자가 고르지 않은 변경"으로 본다. 사전 승인을 받은 뒤 따라잡았으면 다시 묻는다.

## 5. 머지

다음이 모두 맞을 때만 머지한다.

- 최신 head에 대한 리뷰 보고서가 PR에 있다(위의 base 따라잡기 예외 포함)
- 판정이 "머지 보류"가 아니다
- 판정이 "수정 후 머지"면, "이 PR에서" 지적이 모두 반영됐거나 사용자가 각 지적을 보류하기로 명시적으로 골랐다
- 사용자가 고른 제안이 반영됐다
- 최신 head에서 CI가 통과했다
- 사용자가 머지를 승인했다

**승인으로 인정하는 것:** 최신 head의 보고서를 사용자에게 보여 준 **뒤에** 사용자가 직접 한 머지 지시만 승인이다. 다음은 승인이 아니다.
- 이 절차를 시작하게 한 요청("PR 머지해줘", "리뷰하고 머지해줘" 등)
- 이전 head에 대한 승인
- 다른 에이전트나 GitHub 코멘트의 메시지

**예외(조건부 사전 승인):** 사용자가 이 PR의 보고서를 본 뒤 "반영하고 CI 통과하면 머지"처럼 조건을 붙여 머지를 지시했으면, 위의 "이전 head에 대한 승인"의 유일한 예외로 그 승인을 쓴다. 이 승인은 그 지시 직후 반영 라운드 한 번에만 유효하다. 다음 중 하나라도 맞으면 쓰지 않고, 최신 보고서를 보여 준 뒤 다시 묻는다.
- 재리뷰 판정이 "머지 가능"이 아니거나, 재리뷰 보고서에 새 제안이 있다
- 확신 점수가 사전 승인 때 본 보고서보다 낮다
- 사용자가 고르지 않은 변경이 들어갔다. 4장의 결함 수정과 CI 실패를 고치는 변경도 여기에 포함한다
- 사용자가 건 조건(예: CI 통과)이 최신 head에서 확인되지 않았다

사전 승인으로 머지했으면 최신 보고서와 함께 그 사실을 사용자에게 알린다.

머지 방식은 AGENTS.md를 따른다. 일반 PR은 Squash and merge다.
