## 목표와 차별점

- [결정] turbopuffer류의 오픈소스 대안. 억 단위 이상 벡터, 응답 속도는 다소 양보 가능, 운영 단순성과 scalability와 비용 효율이 우선.
- [결정] 차별점 가설: simple but efficient(비용과 성능 모두)한 분산 시스템. 기존 시스템은 기존 primitive 위에 올려서 기능은 그대로 쓸 수 있지만 구성이 복잡하고 장애 시 운영이 어렵다. 사용자 경험: ES master 노드 한 대 이탈 시 클러스터 불안정, force merge 중 OOM으로 노드가 죽고 복귀하지 못함.
- [미정] "이거면 쓴다"는 최소 조건(갱신 시간, 비용, 필터 recall의 숫자). M0가 판정하도록 설계되어 있음.
- [제안] 코디네이터 노드 없이 오브젝트 스토리지 CAS로 메타데이터를 관리하고, 백그라운드 작업은 서비스 노드와 분리해 메모리 상한을 둔다. M0의 S10 시나리오로 검증.

## 워크로드와 요구사항

- [결정] 규모는 억 단위 이상. item당 벡터는 수 개~수십 개(바뀔 수 있음).
- [결정] 쿼리: user embedding은 offline, 유저 history의 각 item에 대해 ANN(요청당 N개 fan-out).
- [결정] OLTP 우선. OLAP는 S3의 SoT 파일을 분석할 수 있으면 충분. 실제 분석 패턴(조인 + group by 배치로 추정)은 불확실.
- [결정] 필터를 first class로. 모든 selectivity와 조건 종류(equality, IN, range, AND/OR)에 대응.
- [결정] 업데이트는 실시간. 벡터 변경과 메타데이터 변경을 구분. 변경 비율이 다양하므로 엔진이 측정해서 경로를 자동 선택하고, 기본 목표는 비용 최소화, 예상 시간과 비용을 알려 주고 사용자가 조정.
- [결정] 일관성: strong 기본(쓴 직후 보임, turbopuffer와 같은 방식), 쿼리별 eventual 선택 가능. eventual 지연은 몇 초~최대 1분(불확실). workload별 freshness 설정 가능.
- [결정] BM25/하이브리드 포함, 한국어 지원 필수(기본 토크나이저로 시작).
- [결정] API는 turbopuffer와 공통 기능을 최대한 호환, 고유 기능은 확장.
- [결정] recall@10 90~95%(필터 쿼리 포함), p99 1초 이하, 비용은 turbopuffer와 comparable(계산기로 추정, 직접 측정 안 함).
- [결정] 모니터링은 처음부터 OpenTelemetry 같은 오픈 스펙. 무중단 업그레이드, 오토스케일, 백업 같은 운영 기능은 SaaS 단계에서.

## 기술 선택

- [결정] Rust, DDD와 ports & adapters, 컴포넌트는 오픈소스를 적극 활용하고 결과물도 오픈소스로. 양자화도 포트로 두어 선택 가능.
- [결정] 인프라는 AWS로 시작, 다른 클라우드도 선택적으로, 온프렘은 나중.
- [결정] 개발 순서: 단일 노드 correctness → 단일 노드 안의 shard/분산 구조 → 실제 분산 노드. M0를 진행하면서 M1의 기본 단위를 병행. 버려도 배움이 남으면 괜찮음.
- [결정] M1의 WAL과 manifest는 직접 구현한 뒤 SlateDB 어댑터와 비교.
- [결정] 프로젝트 이름은 seabed(이름 충돌은 직접 확인 필요: crates.io, GitHub, 도메인, 상표).
- [결정] 라이선스와 SaaS 운영 주체는 공개 시점에 결정.
- [제안] segment 파일은 끝에 footer TOC(섹션 오프셋, 길이, SHA-256), manifest에 임베딩 모델 id와 차원, 거리 지표, 양자화, 토크나이저를 기록하고 불일치 시 즉시 실패(memvid 참고).
- [제안] 쓰기 응답에 LSN 기반 일관성 토큰, 쿼리에 min_lsn(Loams 참고). ES와 Qdrant 호환 API 어댑터도 후보.
- [제안] bulk 경로: 외부 파일 등록(zero-copy), 파티션 단위 병렬 인덱스 빌드와 재개, manifest 교체로 원자적 공개. 경로는 증분 / 부분 재빌드 / 전체 재빌드 중 파티션 단위로 선택.

## 평가(M0)

- [결정] 로컬 우선(S3 호환 에뮬레이터, 조건부 쓰기를 conformance 테스트로 확인한 것만 사용). AWS 예산은 월 몇 달러 수준이라 지연 측정만 짧게 사용. 규모는 머신이 버티는 선까지 설정값으로.
- [결정] 기준선: Chroma, Lance, Milvus, Qdrant, VectorChord, turbopuffer(계산기 추정).
- [제안] VectorDBBench를 러너로, 필터 워크로드는 HCBGen(α-Hardness) 재사용 또는 확장. 시나리오 S1~S10(S10은 운영 단순성과 장애 복구).
- [참고 기준선] 기존 사례: ES에서 200TB 전체 갱신에 일주일(시간당 약 1.2TB). 1차 목표(제안)는 10배 이상.

## 확인하지 못한 것

- VecBench 코드 공개 여부, HCBGen 라이선스와 동작, VectorDBBench의 클라이언트 범위와 라이선스
- Chroma 분산 모드의 오픈소스 범위, Lance의 OSS와 Enterprise 경계, SlateDB의 라이선스와 성숙도
- mecab-ko-dic 사전 라이선스, turbopuffer 공식 가격
- Pinecone 등 비공개 SaaS와 범용 DB의 벡터 기능

## 열린 연구 질문 (계획 문서 9절 참고)

필터-벡터 상관관계에서 recall 보장, doc id 기반 속성 인덱스와 클러스터의 변환 비용, 적응형 클러스터 확장의 비용,
multi-vector에서 over-fetch 최소화와 FDE의 교차점, 접근 로그 기반 클러스터 재배치, bulk와 컴팩션의 OLTP 격리,
α-Hardness를 플래너 신호로 쓰는 방법, 복합 조건의 selectivity 추정, BM25 코퍼스 통계, 한국어 토크나이저 사전 변경 시 재색인 비용.
